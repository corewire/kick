      Operator model

      The KICK operator, formally

      • Open in ChatGPT
      • Open in Claude

      This page gives a precise, self-contained model of what the KICK controller does. It is written for readers who want to reason about correctness rather than read Go. Every definition corresponds to a concrete piece of the controller, and the invariants at the end are the properties the implementation is designed to preserve.

      Notation is standard set theory and first-order logic. We write 2X2^{X}2X for the power set of XXX, f:X⇀Yf : X \rightharpoonup Yf:X⇀Y for a partial function, and ¬, ∧, ∨, ⇒\lnot,\ \land,\ \lor,\ \Rightarrow¬, ∧, ∨, ⇒ for the usual connectives.

      1. Objects and state

      Let a point in time be t∈R≥0t \in \mathbb{R}_{\ge 0}t∈R≥0​. The observable cluster state at time ttt is a tuple

      C(t)=( W,  S,  data,  tmpl,  rs ), \mathcal{C}(t) = \big(\, W,\; S,\; \mathsf{data},\; \mathsf{tmpl},\; \mathsf{rs} \,\big), C(t)=(W,S,data,tmpl,rs),

      whose components are:

      • WWW — the set of workloads. Each w∈Ww \in Ww∈W has a kind κ(w)∈{Deployment, StatefulSet, DaemonSet}\kappa(w) \in \{\textsf{Deployment},\ \textsf{StatefulSet},\ \textsf{DaemonSet}\}κ(w)∈{Deployment, StatefulSet, DaemonSet} and a namespace ns(w)\mathsf{ns}(w)ns(w).
      • SSS — the set of sources, i.e. objects of kind Secret\textsf{Secret}Secret or ConfigMap\textsf{ConfigMap}ConfigMap. Each s∈Ss \in Ss∈S has a creation time γ(s)\gamma(s)γ(s), a resource version ρ(s)∈N\rho(s) \in \mathbb{N}ρ(s)∈N, and a last-write time λ(s)=max⁡(γ(s), max⁡m∈mgr(s)τ(m))\lambda(s) = \max\big(\gamma(s),\ \max_{m \in \mathsf{mgr}(s)} \tau(m)\big)λ(s)=max(γ(s), maxm∈mgr(s)​τ(m)), where mgr(s)\mathsf{mgr}(s)mgr(s) are the server-side field-management entries of sss and τ(m)\tau(m)τ(m) is the time the API server recorded for the last write of manager mmm. By construction λ(s)≥γ(s)\lambda(s) \ge \gamma(s)λ(s)≥γ(s), and λ(s)=γ(s)\lambda(s) = \gamma(s)λ(s)=γ(s) for a source never written since its creation.
      • data(s)\mathsf{data}(s)data(s) — the key/value payload of a source (data + binaryData/stringData), together with its type and immutability flag.
      • tmpl(w)\mathsf{tmpl}(w)tmpl(w) — the Pod template of a workload, in particular its annotation map tmpl(w).ann\mathsf{tmpl}(w).\mathsf{ann}tmpl(w).ann.
      • rs(w)\mathsf{rs}(w)rs(w) — for a Deployment, the set of its ReplicaSets; the current one is rs⋆(w)\mathsf{rs}^{\star}(w)rs⋆(w).

      The controller never mutates data\mathsf{data}data; its only write to cluster state is a single annotation on tmpl(w)\mathsf{tmpl}(w)tmpl(w), defined in §8.

      2. Dependency extraction

      A workload consumes a source when its Pod template references it through an environment variable, an envFrom, a volume, or a projected volume source, in any container or init container. Image-pull secrets are not consumed data and are excluded. This is captured by a pure function

      deps:W⟶2S,deps(w)={ s∈S ∣ s is referenced by tmpl(w) as data }. \mathsf{deps} : W \longrightarrow 2^{S}, \qquad \mathsf{deps}(w) = \big\{\, s \in S \ \mid\ s \text{ is referenced by } \mathsf{tmpl}(w) \text{ as data} \,\big\}. deps:W⟶2S,deps(w)={s∈S ∣ s is referenced by tmpl(w) as data}.

      deps\mathsf{deps}deps is deterministic and depends only on tmpl(w)\mathsf{tmpl}(w)tmpl(w); it is insensitive to reference multiplicity, so a source referenced twice contributes once. Its inverse image gives the consumers of a source,

      cons(s)={ w∈W ∣ s∈deps(w) }, \mathsf{cons}(s) = \{\, w \in W \ \mid\ s \in \mathsf{deps}(w) \,\}, cons(s)={w∈W ∣ s∈deps(w)},

      restricted to ns(w)=ns(s)\mathsf{ns}(w) = \mathsf{ns}(s)ns(w)=ns(s).

      3. Fingerprints and relevant change

      To distinguish a change that matters from one that does not, each source is reduced to a content fingerprint by a collision-resistant hash H=SHA-256H = \mathrm{SHA\text{-}256}H=SHA-256:

      ϕ(s)  =  H ⁣( type(s) ∥ imm(s) ∥∥k∈sort(keys)(k∥data(s)[k])) ∈ {0,1}256. \phi(s) \;=\; H\!\Big(\,\textsf{type}(s)\ \Vert\ \textsf{imm}(s)\ \Vert \mathop{\Big\Vert}\limits_{k \in \mathrm{sort}(\mathrm{keys})} \big(k \Vert \mathsf{data}(s)[k]\big)\Big) \ \in\ \{0,1\}^{256}. ϕ(s)=H(type(s) ∥ imm(s) ∥k∈sort(keys)​​(k∥data(s)[k])) ∈ {0,1}256.

      Keys are sorted so the fingerprint is canonical, and only the payload, type, and immutability enter it. Object metadata — labels, annotations, resourceVersion, managed fields — is deliberately excluded. Hence

      ϕ(s)=ϕ(s′)  ⟺  data(s)=data(s′) ∧ type(s)=type(s′) ∧ imm(s)=imm(s′). \phi(s) = \phi(s') \iff \mathsf{data}(s) = \mathsf{data}(s') \ \land\ \textsf{type}(s)=\textsf{type}(s') \ \land\ \textsf{imm}(s)=\textsf{imm}(s'). ϕ(s)=ϕ(s′)⟺data(s)=data(s′) ∧ type(s)=type(s′) ∧ imm(s)=imm(s′).

      A relevant change to a source is exactly a change of ϕ\phiϕ; a change of ρ\rhoρ with fixed ϕ\phiϕ is metadata-only.

      4. The observation store

      The controller maintains a durable partial map from a source identity to a record,

      Ω:Id(S)⇀R,R=( ρseen, ρrel, θ, φ ), \Omega : \mathrm{Id}(S) \rightharpoonup \mathcal{R}, \qquad \mathcal{R} = \big(\,\rho_{\text{seen}},\ \rho_{\text{rel}},\ \theta,\ \varphi\,\big), Ω:Id(S)⇀R,R=(ρseen​, ρrel​, θ, φ),

      where θ\thetaθ is the time of the last relevant change and φ\varphiφ the last relevant fingerprint. When the controller observes a source sss at wall-clock time ttt, the store transition obs\mathsf{obs}obs classifies the event and updates the record:

      obs(Ω,s,t)={Baselines∉dom⁡Ω,NoChangeφ=ϕ(s) ∧ ρseen=ρ(s),MetaOnlyφ=ϕ(s) ∧ ρseen≠ρ(s),Relevantφ≠ϕ(s). \mathsf{obs}(\Omega, s, t) = \begin{cases} \textsf{Baseline} & s \notin \operatorname{dom}\Omega, \\[2pt] \textsf{NoChange} & \varphi = \phi(s)\ \land\ \rho_{\text{seen}} = \rho(s), \\[2pt] \textsf{MetaOnly} & \varphi = \phi(s)\ \land\ \rho_{\text{seen}} \neq \rho(s), \\[2pt] \textsf{Relevant} & \varphi \neq \phi(s). \end{cases} obs(Ω,s,t)=⎩⎨⎧​BaselineNoChangeMetaOnlyRelevant​s∈/domΩ,φ=ϕ(s) ∧ ρseen​=ρ(s),φ=ϕ(s) ∧ ρseen​=ρ(s),φ=ϕ(s).​

      The recorded change time is the crux of baseline correctness:

      θ′={β(s)on Baseline(the source’s last recorded write),ton Relevant(observed “now”),θon NoChange, MetaOnly,β(s)=λ(s). \theta' = \begin{cases} \beta(s) & \text{on }\textsf{Baseline}\quad(\text{the source's last recorded write}),\\ t & \text{on }\textsf{Relevant}\quad(\text{observed “now”}),\\ \theta & \text{on }\textsf{NoChange},\ \textsf{MetaOnly}, \end{cases} \qquad \beta(s) = \lambda(s). θ′=⎩⎨⎧​β(s)tθ​on Baseline(the source’s last recorded write),on Relevant(observed “now”),on NoChange, MetaOnly,​β(s)=λ(s).

      Why baseline uses β(s)\beta(s)β(s) and not ttt or γ(s)\gamma(s)γ(s). A first observation never witnessed the change that produced the content it sees, so it must date that content from evidence. Using the wall-clock observation instant ttt would make freshness depend on a race between “KICK first saw the Secret” and “the ReplicaSet was created”, producing spurious restarts whenever a workload is adopted. Using γ(s)\gamma(s)γ(s) is unsound in the other direction: if sss was written after its creation but before KICK first observed it — KICK was installed, restarting, or its cache had not synced — then γ(s)≤σ(w)\gamma(s) \le \sigma(w)γ(s)≤σ(w) even though the content is newer than the rollout, and since every later observation matches that baseline the change is dismissed as fresh and never reconsidered.

      λ(s)\lambda(s)λ(s) is the tightest evidence the API server records for “when did this content come to be”: it is the latest write the server itself attributes to the object. The baseline therefore takes λ(s)\lambda(s)λ(s) unmodified. The residual ambiguity — the API server stores that instant with second granularity — is handled by carrying change times at sub-second precision (§5), not by widening the baseline: an artificially advanced baseline dates content later than it provably is and causes spurious restarts when KICK adopts an existing cluster.

      Only Baseline\textsf{Baseline}Baseline and Relevant\textsf{Relevant}Relevant enqueue work for the consumers cons(s)\mathsf{cons}(s)cons(s); NoChange\textsf{NoChange}NoChange and MetaOnly\textsf{MetaOnly}MetaOnly are inert.

      5. Timestamp precision

      Kubernetes records object timestamps — creationTimestamp, managedFields entry times, Deployment condition times — with whole-second granularity. Every quantity that enters σ(w)\sigma(w)σ(w) is therefore second-granular, while a change time θ\thetaθ observed by the controller is not. Change times must be carried at sub-second precision at every hop: the durable observation record stores θ\thetaθ as RFC 3339 with nanosecond precision, and the KickRequest status field latestObservedDependencyChange is a metav1.MicroTime rather than a metav1.Time.

      The failure mode is exact. Truncation to whole seconds is the map t↦⌊t⌋t \mapsto \lfloor t \rfloort↦⌊t⌋. Let a relevant change occur at θ=σ(w)+ε\theta = \sigma(w) + \varepsilonθ=σ(w)+ε with 0<ε<1s0 < \varepsilon < 1\mathrm{s}0<ε<1s, so the change is genuinely newer than the rollout it must supersede. Truncation gives ⌊θ⌋=σ(w)\lfloor \theta \rfloor = \sigma(w)⌊θ⌋=σ(w), and because the staleness test Λ(w)>σ(w)\Lambda(w) > \sigma(w)Λ(w)>σ(w) of §6 is strict,

      Λ(w)>σ(w)but⌊Λ(w)⌋≯σ(w), \Lambda(w) > \sigma(w) \quad\text{but}\quad \lfloor \Lambda(w) \rfloor \not> \sigma(w), Λ(w)>σ(w)but⌊Λ(w)⌋>σ(w),

      so the workload is wrongly declared fresh and the change is lost. Any change falling in the same second as the rollout it supersedes is affected. Hence no component on the path from the observation store to the freshness comparison — record serialisation, status write, status read, coalescing — may truncate.

      6. Rollout state and the freshness relation

      For a workload www the rollout inspector returns a start time and a completeness flag,

      R(w)=(σ(w), complete(w)). \mathsf{R}(w) = \big(\sigma(w),\ \mathrm{complete}(w)\big). R(w)=(σ(w), complete(w)).

      The start time is the latest moment at which the currently-running Pod template is provably in place. Writing cond(w)\mathrm{cond}(w)cond(w) for the workload’s status conditions and υ(c)\upsilon(c)υ(c) for the lastUpdateTime of a condition ccc, or its lastTransitionTime when the former is unset:

      σ(w)={tmpl(w).ann[restartedAt]if that annotation is set,max⁡(γ ⁣(rs⋆(w)), max⁡c ∈ cond(w)υ(c))κ(w)=Deployment,max⁡(γ(w), max⁡c ∈ cond(w)υ(c))κ(w)=DaemonSet,γ(w)κ(w)=StatefulSet, \sigma(w) = \begin{cases} \mathsf{tmpl}(w).\mathsf{ann}[\textsf{restartedAt}] & \text{if that annotation is set},\\[4pt] \max\Big(\gamma\!\big(\mathsf{rs}^{\star}(w)\big),\ \max\limits_{c\,\in\,\mathrm{cond}(w)} \upsilon(c)\Big) & \kappa(w)=\textsf{Deployment},\\[6pt] \max\Big(\gamma(w),\ \max\limits_{c\,\in\,\mathrm{cond}(w)} \upsilon(c)\Big) & \kappa(w)=\textsf{DaemonSet},\\[6pt] \gamma(w) & \kappa(w)=\textsf{StatefulSet}, \end{cases} σ(w)=⎩⎨⎧​tmpl(w).ann[restartedAt]max(γ(rs⋆(w)), c∈cond(w)max​υ(c))max(γ(w), c∈cond(w)max​υ(c))γ(w)​if that annotation is set,κ(w)=Deployment,κ(w)=DaemonSet,κ(w)=StatefulSet,​

      with max⁡c∈∅υ(c)=−∞\max_{c \in \varnothing} \upsilon(c) = -\inftymaxc∈∅​υ(c)=−∞. For a Deployment the current ReplicaSet’s creation time is advanced to the latest condition update, which is effectively the moment the rollout became available and complete. This is deliberate: σ(w)\sigma(w)σ(w) must be the latest instant that is provably true, because a source change may only be dismissed when the running Pods provably already carry it. A DaemonSet falls back to its latest condition transition when one is present; upstream rarely populates DaemonSet conditions, so in practice the creation time is used.

      For StatefulSets and DaemonSets no comparable completion timestamp exists, so σ(w)\sigma(w)σ(w) there is only a lower bound on when the Pods began running. A source created after the workload object but before its Pods started is consequently counted as newer and produces exactly one adoption restart. Manifest ordering makes this rare — Helm and Argo CD apply Secrets and ConfigMaps before the workloads that consume them — and one extra restart is the safe side of the ambiguity.

      Completeness is kind-aware — this is what lets non-Deployment workloads be evaluated at all:

      complete(w)={(rs⋆(w)≠∅) ∧ ¬InProgress(w) ∧ ¬Failed(w)κ(w)=Deployment,observedGen(w)=gen(w) ∧ replicas up to dateκ(w)∈{StatefulSet,DaemonSet}. \mathrm{complete}(w) = \begin{cases} \big(\mathsf{rs}^{\star}(w)\neq\varnothing\big)\ \land\ \lnot\text{InProgress}(w)\ \land\ \lnot\text{Failed}(w) & \kappa(w)=\textsf{Deployment},\\[4pt] \mathrm{observedGen}(w) = \mathrm{gen}(w)\ \land\ \text{replicas up to date} & \kappa(w)\in\{\textsf{StatefulSet},\textsf{DaemonSet}\}. \end{cases} complete(w)={(rs⋆(w)=∅) ∧ ¬InProgress(w) ∧ ¬Failed(w)observedGen(w)=gen(w) ∧ replicas up to date​κ(w)=Deployment,κ(w)∈{StatefulSet,DaemonSet}.​

      Given the dependency scope D(w)⊆deps(w)D(w) \subseteq \mathsf{deps}(w)D(w)⊆deps(w) selected by the policy (§7), the latest relevant change seen for www is

      Λ(w)  =  max⁡ d ∈ D(w) ∩ dom⁡ΩΩ(d).θ,Λ(w)=−∞  if the set is empty. \Lambda(w) \;=\; \max_{\,d \,\in\, D(w)\,\cap\,\operatorname{dom}\Omega} \Omega(d).\theta, \qquad \Lambda(w) = -\infty \ \text{ if the set is empty.} Λ(w)=d∈D(w)∩domΩmax​Ω(d).θ,Λ(w)=−∞  if the set is empty.

      The workload is stale exactly when its rollout is complete yet older than the latest relevant dependency change:

       stale(w)    ⟺    complete(w) ∧ Λ(w)>σ(w)  \boxed{\ \mathrm{stale}(w) \;\iff\; \mathrm{complete}(w)\ \land\ \Lambda(w) > \sigma(w)\ }  stale(w)⟺complete(w) ∧ Λ(w)>σ(w) ​

      If ¬ complete(w)\lnot\,\mathrm{complete}(w)¬complete(w) the workload is in progress and no freshness decision is taken (the request waits). The comparison Λ(w)>σ(w) \Lambda(w) > \sigma(w)Λ(w)>σ(w) is strict, so equal timestamps count as fresh.

      7. Policy scope and the gate

      A KickPolicy selects which workloads it manages and which of their dependency changes may trigger a restart, via two label selectors:

      D(w)={ s∈deps(w) ∣ labels(s)⊨dependencySelector },w managed  ⟺  labels(w)⊨workloadSelector. D(w) = \{\, s \in \mathsf{deps}(w) \ \mid\ \mathsf{labels}(s) \models \text{dependencySelector} \,\}, \qquad w \text{ managed} \iff \mathsf{labels}(w) \models \text{workloadSelector}. D(w)={s∈deps(w) ∣ labels(s)⊨dependencySelector},w managed⟺labels(w)⊨workloadSelector.

      The gate decides whether a permitted-in-principle restart may run now:

      G:W×R≥0→{Allowed}∪{Blocked(r):r∈Q}, \mathsf{G} : W \times \mathbb{R}_{\ge 0} \to \{\textsf{Allowed}\} \cup \{\textsf{Blocked}(r) : r \in \mathcal{Q}\}, G:W×R≥0​→{Allowed}∪{Blocked(r):r∈Q},

      with blocking reasons Q={OutsideSchedule, OwnerUnknown, MultipleOwners, OutOfSync, SyncInProgress,… }\mathcal{Q} = \{\textsf{OutsideSchedule},\ \textsf{OwnerUnknown},\ \textsf{MultipleOwners},\ \textsf{OutOfSync},\ \textsf{SyncInProgress},\dots\}Q={OutsideSchedule, OwnerUnknown, MultipleOwners, OutOfSync, SyncInProgress,…}. It is evaluated in two stages. First, KICK-native schedule windows, if any, are applied: a set of allow/deny cron windows {(kindi,croni,duri)}\{(\text{kind}_i,\text{cron}_i,\text{dur}_i)\}{(kindi​,croni​,duri​)} induces the predicate

      open(t)  =  (∃i: kindi=Allow ∧ t∈windowi) ∧ (¬∃j: kindj=Deny ∧ t∈windowj), \mathrm{open}(t) \;=\; \Big(\exists i:\ \text{kind}_i=\textsf{Allow}\ \land\ t \in \mathrm{window}_i\Big)\ \land\ \Big(\lnot\exists j:\ \text{kind}_j=\textsf{Deny}\ \land\ t \in \mathrm{window}_j\Big), open(t)=(∃i: kindi​=Allow ∧ t∈windowi​) ∧ (¬∃j: kindj​=Deny ∧ t∈windowj​),

      and ¬open(t)\lnot\mathrm{open}(t)¬open(t) yields Blocked(OutsideSchedule)\textsf{Blocked}(\textsf{OutsideSchedule})Blocked(OutsideSchedule). Second, the GitOps provider P∈{None,Auto,ArgoCD,Flux}P \in \{\textsf{None},\textsf{Auto},\textsf{ArgoCD},\textsf{Flux}\}P∈{None,Auto,ArgoCD,Flux} is consulted. With P=NoneP=\textsf{None}P=None (the default) KICK self-gates and the stage returns Allowed\textsf{Allowed}Allowed. Otherwise the owner-resolution relation own(w)\mathsf{own}(w)own(w) must yield exactly one owner whose application is reconciled/synced:

      G(w,t)=Allowed  ⟺  open(t) ∧ (P=None ∨ (∣own(w)∣=1 ∧ synced(own(w)))). \mathsf{G}(w,t) = \textsf{Allowed} \iff \mathrm{open}(t)\ \land\ \Big(P=\textsf{None}\ \lor\ \big(|\mathsf{own}(w)|=1\ \land\ \mathrm{synced}(\mathsf{own}(w))\big)\Big). G(w,t)=Allowed⟺open(t) ∧ (P=None ∨ (∣own(w)∣=1 ∧ synced(own(w)))).

      8. The restart action

      Restarting is the single side effect KICK performs on a workload. It stamps the Pod template with the standard annotation, which forces the workload controller to roll a new revision:

      A(w) :tmpl(w).ann[restartedAt]  ←  now. \mathsf{A}(w)\ :\quad \mathsf{tmpl}(w).\mathsf{ann}[\textsf{restartedAt}] \;\leftarrow\; \mathrm{now}. A(w) :tmpl(w).ann[restartedAt]←now.

      By the definition of σ\sigmaσ in §6, immediately after A(w)\mathsf{A}(w)A(w) we have σ(w)=now≥Λ(w)\sigma(w) = \mathrm{now} \ge \Lambda(w)σ(w)=now≥Λ(w), so the workload is no longer stale. KICK writes no other state: no content hashes, no environment variables, no owner annotations. The action is the only writer of restartedAt\textsf{restartedAt}restartedAt in this model.

      9. The KickRequest transition system

      Discovery and coalescing (§10) produce at most one KickRequest per target workload. A request is a state machine over phases

      Φ={Pending, WaitingForGate, WaitingForOwner, WaitingForApplicationSync, WaitingForRollout, Executing, Succeeded, NoLongerRequired, Failed}, \Phi = \{\textsf{Pending},\ \textsf{WaitingForGate},\ \textsf{WaitingForOwner},\ \textsf{WaitingForApplicationSync},\ \textsf{WaitingForRollout},\ \textsf{Executing},\ \textsf{Succeeded},\ \textsf{NoLongerRequired},\ \textsf{Failed}\}, Φ={Pending, WaitingForGate, WaitingForOwner, WaitingForApplicationSync, WaitingForRollout, Executing, Succeeded, NoLongerRequired, Failed},

      with terminal set Term={Succeeded, NoLongerRequired, Failed}\mathsf{Term} = \{\textsf{Succeeded},\ \textsf{NoLongerRequired},\ \textsf{Failed}\}Term={Succeeded, NoLongerRequired, Failed}. Each request carries a rollout marker μ∈{⊥}∪R≥0\mu \in \{\bot\} \cup \mathbb{R}_{\ge 0}μ∈{⊥}∪R≥0​ (the start time of the rollout it is currently driving). One reconcile step δ\deltaδ applied to a non-terminal request evaluates, in order, the gate, the freshness relation, and the executor:

      δ(w)={WaitingForGate/WaitingForOwner/…if G(w,t)=Blocked(r),WaitingForRolloutif G=Allowed ∧ ¬ complete(w),NoLongerRequiredif G=Allowed ∧ complete(w) ∧ ¬ stale(w),Executing→ A(w) Succeededif G=Allowed ∧ stale(w). \delta(w) = \begin{cases} \textsf{WaitingForGate}/\textsf{WaitingForOwner}/\ldots & \text{if } \mathsf{G}(w,t)=\textsf{Blocked}(r),\\[2pt] \textsf{WaitingForRollout} & \text{if } \mathsf{G}=\textsf{Allowed}\ \land\ \lnot\,\mathrm{complete}(w),\\[2pt] \textsf{NoLongerRequired} & \text{if } \mathsf{G}=\textsf{Allowed}\ \land\ \mathrm{complete}(w)\ \land\ \lnot\,\mathrm{stale}(w),\\[2pt] \textsf{Executing} \xrightarrow{\ \mathsf{A}(w)\ } \textsf{Succeeded} & \text{if } \mathsf{G}=\textsf{Allowed}\ \land\ \mathrm{stale}(w). \end{cases} δ(w)=⎩⎨⎧​WaitingForGate/WaitingForOwner/…WaitingForRolloutNoLongerRequiredExecuting A(w) ​Succeeded​if G(w,t)=Blocked(r),if G=Allowed ∧ ¬complete(w),if G=Allowed ∧ complete(w) ∧ ¬stale(w),if G=Allowed ∧ stale(w).​

      The executor issues the physical restart only on the transition into Executing\textsf{Executing}Executing when the request has no in-flight rollout (μ=⊥\mu=\botμ=⊥); while μ≠⊥\mu\neq\botμ=⊥ it merely watches the rollout to completion.       11. Invariants

      We collect the properties the operator maintains. Let a run be an infinite fair sequence of reconcile steps under a scheduler that eventually delivers every enqueued event.

      (I1) No spurious restart at baseline. If a source sss was last written no later than its consumer’s rollout, λ(s)≤σ(w)\lambda(s) \le \sigma(w)λ(s)≤σ(w), and no relevant change occurs, then Λ(w)≤σ(w)\Lambda(w) \le \sigma(w)Λ(w)≤σ(w) and hence ¬ stale(w)\lnot\,\mathrm{stale}(w)¬stale(w); by §9 the request settles in NoLongerRequired\textsf{NoLongerRequired}NoLongerRequired and A(w)\mathsf{A}(w)A(w) never fires. (Ensured by β(s)=λ(s)\beta(s)=\lambda(s)β(s)=λ(s), §4.) Conversely, if sss was written after the rollout started, λ(s)>σ(w)\lambda(s) > \sigma(w)λ(s)>σ(w), the workload is genuinely stale and is restarted exactly once: KICK adopting it late does not make it fresh.

      (I2) Eventual restart on relevant change. If at time t⋆t^\start⋆ a relevant change gives Λ(w)=t⋆>σ(w)\Lambda(w) = t^\star > \sigma(w)Λ(w)=t⋆>σ(w), and from some time on G(w,⋅)=Allowed\mathsf{G}(w,\cdot)=\textsf{Allowed}G(w,⋅)=Allowed and the workload’s rollout is complete, then in every run A(w)\mathsf{A}(w)A(w) eventually fires and afterwards σ(w)≥t⋆\sigma(w) \ge t^\starσ(w)≥t⋆. (Ensured by reopen resetting μ←⊥\mu\leftarrow\botμ←⊥, §10.)

      (I3) Kind-agnostic freshness. stale(w)\mathrm{stale}(w)stale(w) is well-defined and satisfiable for every κ(w)∈{Deployment,StatefulSet,DaemonSet}\kappa(w) \in \{\textsf{Deployment},\textsf{StatefulSet},\textsf{DaemonSet}\}κ(w)∈{Deployment,StatefulSet,DaemonSet}, because completeness is defined per kind and does not require a ReplicaSet. (Ensured by the kind-aware complete\mathrm{complete}complete, §6.)

      (I4) At most one active request per target. At every reconcile boundary, ∣{ r:target(r)=w ∧ phase(r)∉Term }∣≤1\big|\{\,r : \mathrm{target}(r)=w \ \land\ \mathrm{phase}(r)\notin\mathsf{Term}\,\}\big| \le 1​{r:target(r)=w ∧ phase(r)∈/Term}​≤1. Duplicate and repeated references to the same source therefore cause at most one concurrent restart. (Ensured by the keyed coalescer, §10.)

      (I5) Gate safety. A(w)\mathsf{A}(w)A(w) fires only from the Executing\textsf{Executing}Executing transition, which is reachable only when G(w,t)=Allowed\mathsf{G}(w,t)=\textsf{Allowed}G(w,t)=Allowed. Equivalently,

      A(w) fires at t ⟹ G(w,t)=Allowed. \mathsf{A}(w)\ \text{fires at } t \ \Longrightarrow\ \mathsf{G}(w,t)=\textsf{Allowed}. A(w) fires at t ⟹ G(w,t)=Allowed.

      (I6) Idempotence / no rollout amplification. After A(w)\mathsf{A}(w)A(w) at time t′t't′ with t′≥Λ(w)t' \ge \Lambda(w)t′≥Λ(w), we have σ(w)=t′≥Λ(w)\sigma(w)=t' \ge \Lambda(w)σ(w)=t′≥Λ(w), so ¬ stale(w)\lnot\,\mathrm{stale}(w)¬stale(w) and no further restart is issued until a new relevant change advances Λ\LambdaΛ. A single change thus yields exactly one new rollout.

      (I7) Non-injection. The only workload write is A\mathsf{A}A, setting the standard restartedAt\textsf{restartedAt}restartedAt annotation. KICK injects no dependency hashes, no environment, and no owner state into managed workloads, and never treats imagePullSecrets as dependencies (§2). Secret values never appear in status, events, or logs.

      (I8) Source-driven evaluation. A workload is evaluated only when KICK observes a Baseline\textsf{Baseline}Baseline or Relevant\textsf{Relevant}Relevant event for one of its in-scope sources; there is no workload-driven evaluation. Consequently a workload created after every source in D(w)D(w)D(w) has already been observed carries no KickRequest at all. This is sound: the Pods of such a workload started from the current content of every source, so Λ(w)≤σ(w)\Lambda(w) \le \sigma(w)Λ(w)≤σ(w) and ¬ stale(w)\lnot\,\mathrm{stale}(w)¬stale(w) would hold if the request existed. The absence of a request is the correct no-op, not a missed restart.

      12. Reading the pipeline as one relation

      Composing the pieces, the end-to-end effect of a relevant change to a source sss on a managed, in-scope consumer w∈cons(s)w \in \mathsf{cons}(s)w∈cons(s) is

      ϕ changes⏟observation ⇒ Λ(w)>σ(w)⏟freshness ∧ G(w,t)=Allowed⏟gate ⇒ A(w)⏟restart. \underbrace{\phi\ \text{changes}}_{\text{observation}} \ \Rightarrow\ \underbrace{\Lambda(w) > \sigma(w)}_{\text{freshness}} \ \land\ \underbrace{\mathsf{G}(w,t)=\textsf{Allowed}}_{\text{gate}} \ \Rightarrow\ \underbrace{\mathsf{A}(w)}_{\text{restart}}. observationϕ changes​​ ⇒ freshnessΛ(w)>σ(w)​​ ∧ gateG(w,t)=Allowed​​ ⇒ restartA(w)​​.

      Everything else the controller does — coalescing, phase transitions, retention — exists to make this implication hold exactly once per change, only when permitted, and uniformly across workload kinds.
