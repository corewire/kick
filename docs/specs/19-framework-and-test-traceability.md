# Framework and feature-to-test traceability

## Framework decision

KICK MUST be implemented as a Go operator scaffolded with **Kubebuilder** and built directly on `controller-runtime`.

Required foundation:

- Kubebuilder project layout;
- `controller-runtime` manager, clients, caches, indexes, watches, predicates, and leader election;
- `controller-gen` for CRDs, RBAC, and generated code;
- Envtest for Kubernetes API integration tests;
- Kustomize manifests generated by Kubebuilder;
- a separately maintained Helm chart for installation;
- Kind and Chainsaw for end-to-end tests.

Operator SDK, OLM bundles, ClusterServiceVersions, catalogs, install modes, and upgrade channels are NOT part of the initial implementation. They MAY be added later without changing the controller architecture.

The implementation MUST NOT introduce an abstraction layer merely to hide `controller-runtime`. Small interfaces around KICK domain behavior are required for testability, but framework primitives should remain recognizable to Kubernetes maintainers.

## Universal testability requirement

Every feature MUST be designed so that its externally visible behavior can be tested deterministically.

Every feature that can reasonably be expressed as both a unit test and an end-to-end test MUST have both.

A feature MAY omit a test level only when that level cannot provide meaningful verification. The omission MUST be recorded in the feature matrix with a concrete rationale. Statements such as “too difficult,” “already indirectly tested,” or “covered elsewhere” are insufficient.

Examples:

- Parsing and comparison logic requires unit tests.
- Watch, cache, status, and API interactions require Envtest where useful.
- User-visible controller behavior requires e2e tests.
- Packaging-only behavior may require chart/render tests rather than controller unit tests.
- Documentation-only behavior may use generated-file or link checks rather than e2e tests.

## Stable feature identifiers

Every normative feature MUST have a stable identifier using this format:

```text
KICK-FEAT-NNN
```

Feature IDs MUST remain stable after release. A feature can be deprecated, but its identifier MUST NOT be reassigned.

Every task implementing a feature MUST list its feature IDs. Every relevant test MUST reference at least one feature ID.

## Machine-readable coverage files

The repository MUST contain:

```text
traceability/features.yaml
traceability/e2e-scenarios.yaml
```

`features.yaml` is the source of truth for:

- feature ID;
- short feature name;
- owning specification;
- implementation task;
- required test levels;
- exceptions and rationale;
- expected e2e scenario IDs.

`e2e-scenarios.yaml` maps scenario IDs to:

- Chainsaw directory;
- feature IDs proven by the scenario;
- scenario status;
- optional provider or version constraints.

The implementation repository SHOULD place e2e scenario metadata in each scenario directory and generate the central scenario index from those files. The central file may remain hand-maintained initially if CI verifies it against the directories.

## Coverage checker

CI MUST run a feature-coverage checker. It MUST fail when:

1. a feature requires e2e coverage but has no mapped e2e scenario;
2. a feature requires unit coverage but has no mapped or discoverable unit test;
3. an e2e scenario references an unknown feature ID;
4. a task references an unknown feature ID;
5. a required scenario is marked skipped, disabled, or missing without an approved rationale;
6. a feature marked implemented still has only planned tests;
7. a feature has contradictory test requirements;
8. an obsolete feature or scenario mapping remains after removal.

The first repository version MAY validate unit-test mappings through explicit paths in `features.yaml`. A later version SHOULD discover feature IDs from test names or test metadata.

## Test metadata convention

Go tests SHOULD include feature IDs in the test name or an adjacent comment:

```go
func TestKICK_FEAT_002_ExtractSecretEnvReferences(t *testing.T) {
    // ...
}
```

or:

```go
// Features: KICK-FEAT-002
func TestExtractSecretEnvReferences(t *testing.T) {
    // ...
}
```

Each Chainsaw scenario MUST contain metadata similar to:

```yaml
apiVersion: kick.corewire.io/v1alpha1
kind: TestTrace
metadata:
  name: secret-envfrom-kick
spec:
  scenarioID: KICK-E2E-001
  features:
    - KICK-FEAT-002
    - KICK-FEAT-004
    - KICK-FEAT-013
```

This metadata is for repository tooling and does not need to be installed in the cluster. A simple `trace.yaml` file using the same fields is acceptable.

## Feature coverage report

CI MUST produce a human-readable report containing at least:

| Feature | Unit | Envtest | E2E | Required E2E scenarios | Result |
|---|---:|---:|---:|---|---|

The report MUST distinguish:

- required and passing;
- required but missing;
- planned but not implemented;
- intentionally not applicable with rationale;
- failing or disabled.

The report SHOULD be published as a CI artifact and summarized in pull requests.

## Pull-request rule

A pull request that introduces or changes user-visible behavior MUST update all of the following in the same change:

1. the relevant specification;
2. the feature matrix;
3. unit tests where applicable;
4. Envtest tests where applicable;
5. e2e scenarios where applicable;
6. documentation and examples where behavior is user-visible.

A feature is not complete merely because its implementation compiles. It is complete only when its required traceability entries and tests pass.

## Acceptance criteria

- The project is recognizably a plain Kubebuilder/controller-runtime project.
- No Operator SDK or OLM dependency is required for development or installation.
- Every normative feature has a feature ID.
- Every implemented user-visible feature is mapped to at least one e2e scenario unless explicitly and convincingly marked not applicable.
- Every testable pure behavior has unit tests.
- CI produces and enforces a feature-to-test coverage report.
